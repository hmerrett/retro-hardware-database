# Retro Hardware Database — agent guide

This file is the repository entry point for Codex and other coding agents. The
existing project guidance is authoritative: read `CLAUDE.md` before changing the
project, then read every relevant file under `.claude/rules/`. If this file and a
specific rule disagree, the specific rule wins.

Use British English in code, comments, documentation, tests, and interface copy.

## Before making a change

- Discuss the intended approach before writing code when the scope or behaviour
  is ambiguous.
- Inspect the surrounding implementation and tests; match the existing idiom.
- Check `adr/` for decisions that constrain the change. Record a new ADR when a
  decision changes an interface, shapes the architecture, or would otherwise
  need explaining again.
- Work on a focused branch (`feat/...`, `fix/...`, or another suitable prefix).
  Never commit directly to `main`.

## Architecture

- Keep the application server-rendered with FastAPI and Jinja2. Use plain
  JavaScript where client-side behaviour is needed; do not introduce a frontend
  framework or SPA architecture without an accepted ADR.
- Keep cohesive non-route behaviour in focused modules. `api/app/main.py` is
  being split incrementally: make small, independently verifiable extractions,
  not wholesale rewrites.
- Read configuration from environment variables. Never hard-code deployment
  configuration or secrets, and never commit `.env`.
- Preserve the shared register semantics: computers, parts, and projects draw
  asset identifiers from the same namespace.
- Comments should explain why a choice exists, not narrate what the code does.

## Python and backend work

- Target Python 3.12 and follow the Ruff configuration in `pyproject.toml`.
- Keep runtime dependencies pinned exactly in `api/requirements.txt`. Dependency
  upgrades must be deliberate and accompanied by tests and an audit.
- Validate input at the boundary and return useful HTTP errors without exposing
  internal details.
- Use standard-library logging with lazy `%s` interpolation. Never log secrets,
  credentials, cookies, or session tokens.
- Prefer typed code and improve typing in code being touched, while respecting
  the project's staged move towards strict typing.

## Database work

- Use the shared SQLAlchemy engine, declarative base, and session dependency from
  `api/app/db.py`. Do not construct ad-hoc engines in application code.
- Use the ORM or parameterised queries; never interpolate values into SQL.
- Every schema change requires an Alembic migration with a working downgrade.
- Migrations must succeed on an empty MariaDB database and must not assume that
  installation-specific assets or rows exist.
- Keep one-off corrections to named records out of shared migrations. Put them
  in a deliberate tool script, or make the operation a safe no-op when the row is
  absent.
- Account for MariaDB's non-transactional DDL: avoid migration sequences whose
  partial failure can wedge subsequent starts.
- Review autogenerated migrations and ensure the models and migration head agree.

## Tests and verification

- Every behavioural change needs tests. Prefer a failing test first for features
  and bug fixes, then make it pass and keep the full suite green.
- Name tests for observable behaviour and prefer real code over mocks except at
  genuine I/O boundaries.
- Run `ruff check .` and `pytest` before considering a change complete.
- Database-sensitive work must also be verified against MariaDB, including an
  empty-database `alembic upgrade head`; SQLite alone is not sufficient evidence.
- Run `pip-audit -r api/requirements.txt` when dependencies change.
- Do not weaken, skip, or delete tests merely to make a change pass.

## Security and deployment

- Preserve defence in depth around authentication, signed sessions, rate
  limiting, uploads, outbound requests, and user-supplied files.
- Validate uploaded images by decoding their content, not by trusting filenames
  or declared content types.
- For outbound user-supplied URLs, permit only HTTP(S), require public resolved
  addresses, and validate every redirect hop.
- Keep user-supplied files served as downloads with `nosniff`; do not silently
  change their current public/private policy.
- Only Caddy should be exposed publicly. Application, database, and MCP services
  remain internal or bound to localhost as defined by the Compose architecture.
- Keep deployment-specific branding and proxy configuration outside versioned
  application code.
